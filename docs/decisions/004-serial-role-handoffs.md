# ADR 004：外层串行主图与受限角色交接

日期：2026-10-02

状态：已采用（P04）

## 背景

P03 已有实际工具循环、建议契约、代码验证和事件记录。P04 要学习职责拆分与主图编排，同时保留单 Agent 基线用于之后同条件对照。用户继续采用离线脚本模型；本轮不引入人工待办、写动作或恢复协议。

## 决定

1. 外层 StateGraph 使用 JSON 可序列化 TicketState；intake、order、policy、draft、validate 组成有限串行路径。Route 枚举与 TRANSITIONS 表限定交接，模型不能给出任意节点名。
2. 客服协调在 intake 整理工单声明的意图、原始订单引用、客户陈述、缺口与固定调查计划，在 draft 根据结构化专员结果形成建议。两个阶段各自使用新的消息历史，不将旧模型对话复制进草稿阶段。
3. 订单专员暴露 5 个订单事实读取工具，政策专员仅暴露政策检索/读取/计算工具；协调没有业务工具。共享 ToolSession 注入可信工单范围，并用同一会话证据支持政策计算和最后代码复算。
4. 父图节点调用 create_agent 子图，通过显式投影构造 HumanMessage。订单输入不含客户对话或政策；政策输入不含专员内部 messages，只含订单摘要及引用。输出经 Pydantic 检查、快照来源/内容核对与实际工具结果核对后才能进入父图。
5. 订单号缺失、未知意图跳过调查；订单不可访问后不进入政策。查询错误跨角色保留，不能变为“没有记录”或自动拒绝。
6. 所有角色及最后代码复算使用同一调用预算；schema 修复预算同 run 共用默认 1 次，角色切换不重置。有限脚本允许明确的提前结束反馈路径，未定义调用仍失败；审核返工由 P05 另建共享计数。
7. 单 Agent 与多 Agent 使用同一 ResolutionProposal / 代码验证；草稿的离线规则装配函数复用。multi-run-v1 增加父图状态、角色输入/输出、轨迹与 Mermaid，report show 同时读取旧、新报告。

## 原因与影响

显式父图让依赖顺序可以观察和测试。政策依赖订单事实，P04 先串行实现；P07 才并行不依赖最终事实的政策候选检索。工具白名单限制模型能调用的能力，可信范围和引用验证仍由工具服务负责，两层不能互相替代。

当前专员摘要保留这轮协议所需的完整事实和查询错误，结构化摘要不是一句自由文本结论。严格与实际工具结果对齐会限制角色输出自由度；未来增加任务类型或缩减事实字段时，需要修改交接契约和对应校验，不能只改提示词。

依赖对象放在闭包而非 State，不等于实现了恢复。P04 只验证状态可序列化和静态报告回看，检查点、重新建会话、证据恢复及批准版本在 P05 / P06。报告日志可汇总多个角色的消息，但这些日志不作为其他角色的模型输入。

离线协调按工单类型编排，不衡量任意用户文本的理解能力。三类样例多 Agent 比基线各多 3 次模型调用，业务建议与工具数一致；这只是脚本协议的观察，不是多 Agent 质量或成本优势的证明。

## 验证

- 20 个既有工单基础路径和未知意图分别验证合法节点序列与跳过分支。
- 角色初次调用没有其他角色的 ToolMessage；政策拿到真实订单事实与引用。
- 非法跨角色工具调用不能执行，模型编造事实/引用或改订单在交接处被拒绝。
- schema 合法但超余额的最终退款建议仍被代码验证拒绝。
- 调用上限、schema 修复上限跨角色累计，提前结束后的修复也有界。
- State 经 JSON 和 LangGraph serializer 往返，运行时依赖和密钥不进入载荷。
- 工单测试前后业务库 dump 一致；旧单 Agent 用例和报告回看保持通过。
