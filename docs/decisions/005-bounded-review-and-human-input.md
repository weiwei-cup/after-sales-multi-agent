# ADR 005：有界审核与同进程人工输入

日期：2026-10-02～2026-10-03；状态：已采用；阶段：P05。

## 问题

P04 把事实调查、政策计算和起草拆给三个角色，但遇到失败查询或错误措辞只能停止。售后处理还需要针对反馈返工，并区分客户补资料与操作员确认方案；旧确认不能授权修改后的金额。

## 决定

保留 single 基线和 multi 的 serial 默认入口，新增 `--architecture multi --workflow reviewed`。审核角色通过真实 create_agent 输出 ReviewResult，只有 validate_evidence_refs / get_evidence 工具。应用依据可信 DTO、规则复算及受控中文模板计算最低审核要求；模型可以提出更严格的补查或改写，不能用 accept 覆盖硬性失败。离线脚本审核不代表通用自然语言语义审核或真实模型质量。

代码校验、审核意见、操作员金额修改共同消耗 repair_count，配置只允许 0～2。schema 修复沿用 P03 的独立全局上限。调用预算跨角色、返工和恢复累计；预算耗尽可以早于两次返工上限转人工。

ResearchTask 用角色工具白名单限制补查。订单补查合并实际 ToolMessage，只替换指定来源，保留其他事实和错误。只补凭证时保留政策计算；订单、商品、物流或售后历史改变时重新计算依赖政策，显式记录 dependent_policy_recheck。

PendingInput 区分 customer_info / operator_decision，绑定 run、ticket、输入版本、方案版本和完整方案哈希。action_id 根据运行、动作类型和订单生成；content_hash 覆盖完整动作。客户只能回答列出的字段；操作员只能批准、拒绝或修改当前退款候选的正整数分金额。新金额生成新方案和待办，旧批准被拒绝。模型没有准确应用指定金额时必须继续返工或交人工。

prepare 与 wait 节点分开：prepare 建立稳定待办，wait 的第一项外部输入操作为真实 `interrupt()`。恢复使用 `Command(resume=...)`，等待节点重新执行时不会再次建立待办。应用在进入图前验证 envelope，并用运行级 asyncio.Lock 防止并发重复消费。

本轮用 InMemorySaver，运行对象同时持有证据、预算、待办注册表和确认记录。交互式 CLI 保持对象存活；静态 JSON 只可回看，不能导入为可信证据或恢复检查点。客户回答写入内存输入修订；补订单号后重新核验归属，其他回答保留为未核验陈述，不修改业务事实。

## 边界与代价

- 本地客户/操作员身份由演示入口注入，envelope 的角色与 ID 检查不等于生产鉴权；认证接口在 P08 实现。
- completed 表示建议审核及必要确认结束；executed_actions 始终为空，不改变工单业务状态或退款余额。
- 批准前复算仍使用当前运行可信快照和固定业务时间。执行前读取最新版本与时钟、持久恢复和业务事务在 P06 实现。
- 内存待办没有崩溃一致性保证；节点抛出 GraphInterrupt 与执行失败分开记录。本轮不提供跨进程 resume 命令。
- 受控模板更容易做确定性验证，但不接受任意等义改写；真实模型语义评估需要后续单独设计。

## 验证

真实临时 SQLite、create_agent 和带 checkpointer 的 StateGraph 验证定向补查、保留证据、依赖重算、共享返工上限、真实 interrupt、角色/版本/内容错配、重复及并发 resume、金额修改、无业务写入、静态报告一致性和交互式 CLI。实现与实测见 [第 005 轮记录](../rounds/005.md)。
