# 第 001 轮：业务模型和模拟资料（P01）

日期：2026-10-02；依赖：已完成的 P00；下一轮：P02 工具、规则与证据。

## 本轮业务目标

先让系统具备真实可查询的资料，后续 Agent 才能调查、引用和提出建议。现在可以查询订单、物流、凭证、售后历史和有效政策，得到固定、可复现的结果。

## 五个实现步骤

1. **定义业务契约**：[models.py](../../src/after_sales/domain/models.py) 定义客户、商品、订单、工单、消息、凭证、政策、历史和运行模型。金额采用整数分，时间校验时区并转 UTC。业务状态和 run 状态分别定义。
2. **建立存储**：[migrations.py](../../src/after_sales/repositories/migrations.py) 建立版本化 schema；[sqlite.py](../../src/after_sales/repositories/sqlite.py) 提供连接、事务、只读查询和客户范围约束。SQLite 外键需要逐连接启用。
3. **准备固定资料**：[demo-v1.json](../../src/after_sales/data/demo-v1.json) 提供 30 条订单与 20 个工单。[seed.py](../../src/after_sales/repositories/seed.py) 一次校验后原子写入，重复执行不覆盖运行后的状态。
4. **建立 CLI**：[cli.py](../../src/after_sales/cli.py) 新增 seed、迁移、工单、订单和政策查询。默认工单文本采用上海时间，`--json` 保留 UTC，方便后续工具使用。
5. **保存独立测试预期**：[案例说明](../../fixtures/README.md) 列出开发与留出输入；预期结果另存 gold，不加入运行时资料。后续实现各阶段时逐个验证业务行为。

## 演示顺序

```bash
./scripts/dev run --locked after-sales seed --dataset demo
./scripts/dev run --locked after-sales ticket show T-DELAY-001
./scripts/dev run --locked after-sales ticket show T-NOTRECEIVED-001
./scripts/dev run --locked after-sales ticket show T-RETURN-001
./scripts/dev run --locked after-sales ticket show T-CROSS-001 --json
./scripts/dev run --locked after-sales policy show RETURN-STANDARD --version 2 --json
```

可以观察：三类工单有不同资料；普通退货使用当前 v1；未来 v2 可以按版本复核，但不自动进入当前候选；跨客户工单只保留原始引用，不返回对方业务资料。

## 本轮需要理解的概念

| 概念 | 在项目中的例子 |
| --- | --- |
| 业务数据与模型输出 | 订单实付和物流事件来自 repository，Agent 后续只能读取引用这些资料 |
| 用户输入与可信关联 | supplied_order_id 可错误，order_id 必须经过归属核验 |
| 业务状态与运行状态 | 登记退货后可以 run completed，但业务仍 waiting_return |
| 事务与幂等初始化 | seed 失败整体回滚；重复 seed 不产生第二批数据 |
| 固定时间与版本 | 七天边界按 as_of_time 计算，政策按明确版本和有效期查询 |
| 业务资料与 gold | 同一事实可以产生多种合法回复；gold 在输出之后评价，不提前提供答案 |

本轮尚未实现政策适用性计算、证据引用、工具调用和 Agent 处理。第 002 轮将把这些读取能力包装为受约束的工具，并用代码计算退货窗口、退款余额和政策条件。
