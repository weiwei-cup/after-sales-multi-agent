# 第 006 轮：持久恢复与模拟动作

日期：2026-10-03；对应计划：P06。状态：实现已上传 GitHub，本地与 Linux CI 验收通过，达到离线 M2。

## 本轮业务结果

客户追问、人工确认和执行中断可以在另一个 Python 进程继续。批准后的物流调查、退货登记、模拟退款由动作服务提交，返回有 operation key、金额、业务记录 ID 和提交时间的回执。图运行结束与业务完成分别展示。

| 动作 | 当前图运行 | 工单业务状态 | 业务记录 |
| --- | --- | --- | --- |
| 物流调查登记 | completed | processing | active 调查记录 |
| 退货申请登记 | completed | waiting_return | active 退货记录 |
| 模拟退款 | completed | resolved | completed 退款记录及金额更新 |
| 仅信息答复、拒绝说明 | completed | resolved | 不增加动作记录 |
| 已有有效申请 | completed | 保留 waiting_return / processing 等履约状态 | 跟进已有记录 |
| 不能安全继续或操作员拒绝 | handed_off | handed_off | 保留证据与原因 |

## 按步骤理解实现

### 1. 先分清两种持久化

业务 schema v2 在原 schema 上增加应用运行资料、方案版本、待办和人工回答、动作账本与事件。after_sales_history 增加 operation_key，承载三类模拟业务记录；repository 明确投影 DTO 字段，新增列不会破坏已有查询。

checkpoints.sqlite 使用 AsyncSqliteSaver，保存 LangGraph 的位置和状态。business.sqlite 保存已经接受的人工输入和已提交的业务效果。这两库不能一起原子提交，恢复协议要覆盖二者之间的空隙。

run ID 同时作为 thread ID。workflow、state、model、检查点路径及运行限制随 run 保存；加载时先检查兼容性。证据从应用的 SQLite 记录恢复，并核对范围和内容哈希；不能把 report show 的 JSON 当成恢复资料。

### 2. 人工回答先保存，再进入图

resume 首先验证角色、演示身份、待办、输入/方案版本、完整方案哈希和动作哈希；业务事务再次核对绑定与工单当前输入版本。客户答复与新输入版本、客户消息一同提交。客户的其他声明仍不改写订单事实。

操作员回答产生持久确认，支持 approve / reject / revise。金额修改保持原有 P05 的共享返工上限，新方案重新展示和确认。有效回答保存后才发送 Command(resume=envelope)。

如果进程在保存回答后退出，图仍可能停在等待节点。load 读取 human_inputs 后投影为 interrupted，recover 使用已保存的同一 envelope 重放。客户版本只递增一次，确认按 pending ID 去重，等待节点重进入不产生第二笔业务动作。

### 3. 执行前检查当前资料

ActionService 是确定性应用服务，不作为模型的写工具。它在业务事务内取得批准对应的 active plan，核对方案、待办、批准及规则版本，然后读取最新工单、订单、商品、物流、凭证、历史和政策目录。

比较的是事实与政策内容，而不是新旧 evidence ID。这样既能发现同版本内容被修改，也不会因为执行时钟不同导致哈希变化而误判所有批准失效。时间资格仍必须在执行时按当前 UTC 时钟重算。

资料或资格变化时，旧批准和方案失效。refresh 用已有只读工具更新事实及规则，再走 draft → validate → review；需要动作时生成新 pending 和 proposal_revision。旧金额编辑不沿用到变化后的事实。模型/工具/返工预算继续累计，不能反复重启绕过上限。

### 4. 用账本处理重复与崩溃

operation key 绑定工单、输入版本、动作类型及订单，payload hash 还绑定金额。方案 revision 和 run ID 不构成新的业务请求。重复已提交的同 payload 返回原回执；同 key 换金额产生 DurableInputConflict。对同一输入版本提出第二笔不同金额退款，会转人工，而不会自动补退。

事务写入包含：账本回执、history 业务记录、退款余额和订单版本、工单业务状态、action_committed 事件。提交前退出全部回滚。提交后、图检查点前退出，恢复先查账本，返回原回执；自身新增的退款余额和 history 不会让节点再次退款。

BEGIN IMMEDIATE 将最新事实检查与写入放在同一锁范围；退款还使用带旧版本和余额上界的条件 UPDATE。两个不同工单同时申请同一订单余额，只能有符合最新资料的动作提交；另一笔批准失效。

### 5. 恢复和诊断保持可解释

load 根据真实 graph.next 判断位置：等待且无保存回答保持 paused；已有回答或还有其他待执行节点投影为 interrupted；图已结束则返回最终报告。`resume` 自动恢复 interrupted，然后显示待办或结果。

调用占用在执行前持久化，重启沿用原限制。硬性预算/脚本/交接失败持久转人工，不能靠重启继续追加调用。活动执行时间跨进程累计，等待时间不计入其中；未报告 token usage 仍为 null。

同一 run 和工单的 POSIX 文件锁阻止同时执行，退出自动释放；已存在暂停运行的工单必须 resume。检查点所有权、manifest 和版本检查防止误用其他文件。业务 reset 保留检查点文件，但不允许旧 thread ID 当成新的 run。

persistent-run-v1 同时包含 projected graph_state、原始 checkpoint_state、人工输入历史、确认和已提交回执。检查 interrupted 时，即使图尚未保存最新效果，账本回执也会展示。报告验证检查版本、内容、批准、动作回执及 operation key/payload hash 内部一致；静态一致性不等于来源认证。

## 演示命令

在项目根目录执行。以下退款不受退货窗口影响，适合使用真实当前时钟演示：

```bash
uv run --locked after-sales seed --dataset demo
uv run --locked after-sales run --ticket T-NOTRECEIVED-002 --architecture multi --workflow durable --run-id learning-006
# 命令保存待办后退出；另开一个终端继续。
uv run --locked after-sales resume --run learning-006 --model scripted
# 看清动作后输入 approve。
uv run --locked after-sales ticket show T-NOTRECEIVED-002
uv run --locked after-sales order show ORD-004 --customer CUST-A --json
uv run --locked after-sales resume --run learning-006 --json
```

用新 run ID 开始新的调查；如果工单已有 active run，错误信息给出应 resume 的 ID。可以在交互中 quit/EOF，再恢复。不要在同一订单已全额退款后期待再次生成退款候选。

缺订单与退货流程：

```bash
uv run --locked after-sales run --ticket T-MISSING-001 --architecture multi --workflow durable
uv run --locked after-sales resume --run 上一步的运行ID
# 回答 ORD-019，然后查看当前时间下的退货资格；合法时再批准。
uv run --locked after-sales run --ticket T-DELAY-002 --architecture multi --workflow durable --interactive
```

P06 默认使用实际 UTC 时钟，fixture 的退货窗口会随日期过去而失效；这正是执行前复算的行为。测试和学习轨迹通过可信注入固定 2026-10-02T04:00:00Z。可复现脚本只使用临时数据库，且每次启动独立 Python 进程：

```bash
uv run --locked python scripts/demo_p06.py
```

程序化答复通过 `--response-file` 传入完整 envelope；从当前待办调用 `response_envelope(pending, decision="approve")` 或 `answers=...` 构造。它包含完整绑定，不能仅传一个 approve 字符串或旧方案 ID。重复发送已完成运行的完全相同批准返回原回执。

```bash
uv run --locked after-sales resume --run learning-006 --response-file response.json --json --output var/runs/new-response-report.json
```

report show 读取静态记录；run/resume 保存新文件，已有目标文件会在执行前拒绝，避免发生业务效果后才发现报告无法保存。

| 验证 | 可复核观察 |
| --- | --- |

| 旧版本、错检查点路径、旧 manifest | 明确不兼容，数据库内容保留 |
