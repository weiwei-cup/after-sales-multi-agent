## 本轮业务结果

一个售后 Agent 调用 P02 的只读工具，调查三类工单并输出结构化建议。建议经过独立代码校验后，才能进入 accepted_proposal；仍然不执行退款、退货登记或物流登记。

用户选择暂时只用离线脚本模型，因此本轮没有真实 provider、网络模型请求或模型费用。ScriptedChatModel 参与实际 LangChain create_agent 循环，用真实 ToolMessage 形成下一步调用；不是直接按工单 ID 返回答案。

| 工单 | 实际建议 | 模型调用 | 业务工具调用 | 其中代码复算 |
| --- | --- | --- | --- | --- |
| T-DELAY-001 | inform_progress，继续关注物流进度 | 9 | 8 | 0 |
| T-NOTRECEIVED-002 | propose_refund，10000 分退款候选 | 9 | 9 | 1 |
| T-RETURN-001 | propose_return，退货申请候选 | 8 | 8 | 1 |
| T-CONFLICT-001 | human_review，政策冲突交人工 | 8 | 7 | 0 |

这些是 demo-v1 在固定业务时间下的实际结果。所有运行执行动作数为 0；completed 表示本轮调查/建议结束，工单业务状态没有改为 resolved。缺订单号直接 request_information，不猜订单，不调用业务工具。跨客户查询收到 NOT_OWNED 后停止调查，不返回对方事实。

## 按步骤理解实现

### 1. 从工具结果建立模型脚本

`agents/scripted.py` 定义 ScriptStep 和 ScriptedChatModel。每次模型生成之前检查上一步收到的工具名称和 call ID。响应既可以是固定 AIMessage，也可以是依据当前消息计算的函数；测试可注入明确异常。

`agents/baseline_script.py` 定义有限业务路径。正常顺序为 get_order → get_order_products → get_tracking → get_delivery_proof → get_after_sales_history → search_policies，再逐个调用 evaluate_policy。是否形成退款/退货/调查候选取决于规则工具的实际结果；不合法或未知条件保持问题与缺口。

响应函数只解析 ToolMessage，不直接访问 repository 或 gold。测试将丢件订单实付金额从 10000 分改为 8700 分后，退款候选和余额声明均变成 8700 分。未定义序列、未绑定工具、重复 call ID 或脚本耗尽会诊断失败，不能回退到“看似正确”的回复。

### 2. 运行实际模型与工具循环

`agents/runner.py` 载入工单，创建每轮独立的 ToolSession，可信 customer_id 等仍由应用注入。用户消息作为带 role/content 的资料 JSON 输入；系统提示要求从工具取得事实、保留 unknown、冲突转人工、只生成候选。

create_agent 接收 ScriptedChatModel、10 个只读工具、系统提示、结构化输出策略和中间件。以退货为例：

```text
模型 1 → get_order               → ToolMessage(call_id=script-read-1)
模型 2 → get_order_products      → ToolMessage(call_id=script-read-2)
模型 3 → get_tracking            → ToolMessage(call_id=script-read-3)
模型 4 → get_delivery_proof      → ToolMessage(call_id=script-read-4)
模型 5 → get_after_sales_history → ToolMessage(call_id=script-read-5)
模型 6 → search_policies         → ToolMessage(call_id=script-read-6)
模型 7 → evaluate_policy         → ToolMessage(call_id=script-assess-1)
模型 8 → ResolutionProposal      → 框架校验结构化输出
代码   → evaluate_policy         → 再算候选资格，工具调用计入预算
```

这里有 8 次模型调用、7 次 Agent 业务工具调用和 1 次代码复算。ResolutionProposal 是框架用来交付结构化输出的合成工具，不算业务工具；产生它的模型调用计入模型预算。

### 3. 定义建议，而非执行结果

`agents/contracts.py` 的主要契约：

| 契约 | 核心内容 |
| --- | --- |
| ResolutionProposal | 工单/订单、decision、事实声明、引用、动作候选、问题、中文草稿、candidate_only=true |
| FactClaim | 定义的事实名、值和 evidence_ref |
| ActionCandidate | 动作类型、订单、整数分金额、assessment、政策版本、事实依据、必须操作员确认 |
| ProposalValidation | ok、问题、复算次数、executable=false |
| StoredRunReport | 完整报告结构、运行状态、原始与通过校验的建议、记录与版本 |

Pydantic 检查字段、类型、未知字段和决策关系。例如退款要有正整数分金额，退货不能带金额；request_information 必须带问题；动作必须与 decision 对应。它不能独自证明引用支持结论或退款余额足够。

### 4. 分开验证结构与业务

ToolStrategy 用 Pydantic schema 检查输出。第一次无效会生成真实反馈 ToolMessage，由脚本修复；持续无效以 SchemaRepairExceeded 停止。默认最多修复 1 次，可设置 0～3；这与 P05 的审核返工是不同计数。

`agents/validation.py` 随后验证工单和订单范围、引用存在/版本、声明与实际事实一致、动作和规则 assessment 一致、完整政策依据及规则输入，再用候选金额调用 evaluate_policy 复算。

两个错误示例：

- decision 为 invented-decision：schema 无效，可以有限修复。
- 余额 10000 分但候选金额 10001 分：schema 合法，代码复算返回 ACTION_RULE_RECHECK_FAILED。status 为 validation_failed，原始 proposal 保留，accepted_proposal 为 null，动作数为 0。

代码也拒绝伪造事实、未知引用、错误政策版本和其他订单动作。完整自然语言草稿的语义审核尚未实现；本轮校验的是声明的结构化事实与候选资格。

### 5. 记录调用、耗时与停止原因

`agents/telemetry.py` 在调用前检查模型/业务工具预算，并记录顺序事件、角色、结果、call ID 和耗时。默认 max_model_calls=20、max_tool_calls=30；包括 schema 修复及验证器复算。预算不足时保存诊断失败，不产生通过校验的建议。

模型单次时限默认 30 秒；工具继续使用 P02 的 3 秒时限与结果长度限制。模型或查询异常只记录安全错误类型，不把原始异常中的测试密钥写进报告。查询失败表示“资料未取得”，不能作为政策拒绝或没有记录的事实。

只有模型实际提供 usage 时才记录；脚本模型没有上报时 token_usage=null、token_usage_note=not_reported，不显示费用估计。全局并发/时间/token 预算与暂时性错误重试仍在 P07。

### 6. 保存与回看运行

每轮保存 baseline-run-v1 JSON：输入、框架/脚本/规则/资料版本、业务时间、proposal、accepted_proposal、validation、error、证据、消息、事件和统计。先完整写临时文件，再原子发布到新路径，禁止覆盖已有文件。

report show 读取并校验 StoredRunReport 后展示。运行文件可在程序退出后回看，但不恢复 Agent 状态，不重新注册证据，不证明文件来源，不授权动作。P05 / P06 才增加人工待办、检查点与恢复。

```bash

./scripts/dev run --locked after-sales report show var/runs/运行ID.json --json
```

run 可用 --output 指定新文件；失败/验证不通过退出码 1，未知工单/配置/文件错误为 2，completed 和 skipped 为 0。live-smoke 或显式 run --model live 返回 skipped / LIVE_PROVIDER_DEFERRED，调用数为 0；保留的 live 配置并不代表真实适配器可用。

## 本轮要理解的概念与下一步

| 概念 | 本轮观察点 |
| --- | --- |
| 模型和框架的职责 | 模型发出调用意图，框架执行工具并回传 ToolMessage |
| call ID | 返回必须对应模型调用，不能用未关联资料替代 |
| 结构与事实 | schema 合法的金额仍可能超过可信余额 |
| 候选与授权 | accepted_proposal 通过调查校验，executable 仍为 false |
| 脚本与真实模型 | 脚本验证流程，不能证明语言理解与协作收益 |
| 记录与检查点 | JSON 可回看，不意味着可恢复运行 |
| 调用预算 | 最终输出、修复、应用复算都要计数 |

第 004 轮 / P04 将建立外层 LangGraph TicketState 与串行主图，拆成客服协调、订单物流、售后政策三个职责，限制各自工具和上下文，通过结构化摘要交接。继续复用本轮建议契约、工具、规则和离线模型；审核、人机暂停以及动作执行仍按 P05 / P06 推进。
