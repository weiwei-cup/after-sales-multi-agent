## 3. F1：不适用政策或无效参数能制造“不符合条件”

优先级：P1。影响 P02，并传递到 P03 / P04 的建议生成。

实际反例：`T-RETURN-001 / ORD-005` 使用当前 `RETURN-STANDARD v1` 得到 `eligible`。再通过真实 `get_policy` 读取尚未生效的 v2，将 v1、v2 一起交给 `evaluate_policy`，旧实现返回 `ineligible`。未来版本的 `policy_active=false` 被混入所有条件的合取，错误地否定了当前有效政策。同时，给退货动作传入金额也会产生 `amount_not_applicable=false`，混淆了工具参数错误和客户不满足业务条件。

修复：

- `get_policy` 仍允许读取指定历史或未来版本，供查阅。
- `evaluate_policy` 重新发现当前工单、商品、时间和动作的适用政策；提供不适用的版本或其他动作的政策，返回 `INVALID_ARGUMENT`。
- 非退款评估不允许携带 `requested_amount_cents`。退款负金额、零金额和超余额金额仍由确定性规则判断，原有回归保留。
- 无效调用不产生业务资料或 assessment 证据。省略当前适用政策仍保留原有缺口 / 冲突检测。
- 当前规则记录升级为 `rules-v2`，历史阶段标签仍保留 `rules-v1` 的原始实现。

回归入口：`tests/test_readonly_tools.py` 中未来版本、额外不适用政策和非退款金额的测试。

## 4. F2：任一否定 assessment 都能被当作拒绝整个工单的依据

优先级：P1。影响 P03 / P04 共用的代码校验。

实际反例：`T-NOTRECEIVED-001` 的物流调查候选满足条件，退款候选因为尚无确认丢件证据而不满足。把最终结构化建议改为 `decline_request`、删除动作，旧代码只要求引用中存在任一 `ineligible` assessment，因此单 Agent 和多 Agent 都返回 `completed` 并接纳了错误拒绝。

此外，真实不符合条件的退货 assessment 即使没有绑定建议订单、或未列出完整政策 / 事实输入，旧拒绝校验仍能通过。已有申请结论也只有“存在某个对应 disposition”的检查，缺少同样的关联约束。

修复：

- 拒绝必须对应当前退货请求的 `create_return_request` 规则；物流或退款候选失败不能授权拒绝签收未收到或物流延迟工单。
- 拒绝与已有申请必须绑定当前订单、适合当前意图的动作、对应 assessment 和完整输入引用。
- 从不可变证据重建规则查询，再次计算当前业务请求；复算为 eligible、缺信息、政策冲突或查询失败时，拒绝不能通过。
- 复算使用全运行共享的工具预算，不因“没有动作候选”而绕过预算。
- `ProposalValidation.rechecked_decisions` 记录这类复算，`rechecked_actions` 保留动作候选复算口径。旧报告缺少新字段时默认 0。

回归入口：`tests/test_negative_decisions.py`，以及单 / 多 Agent 的错误拒绝测试。有效拒绝和已有申请仍能通过；预算不足时保存失败诊断且不接纳建议。

## 5. F3：运行报告内部矛盾仍可显示“完成 / 已通过”

优先级：P2。影响报告保存与 CLI 读取，不涉及业务写动作。

旧报告契约允许：报告与已通过建议属于不同工单；原始建议与已通过建议不同；`validation.ok=true` 同时存在错误；`validation_failed` 却携带通过的校验；`completed` 同时携带执行错误。`report show` 会正常读取这些矛盾记录。

修复：

- 已通过建议必须属于报告工单，并与实际校验的原始建议一致。
- 校验结果必须与 issues 一致；完成状态不能携带执行错误；校验失败状态必须保存被拒绝的建议及失败校验。
- 保存与读取共用同一契约。不一致记录在创建输出目录前被拒绝，CLI 返回输入错误。
- 被代码拒绝的错误工单建议仍可作为原始诊断保存；它不能成为 `accepted_proposal`。没有因加强校验而丢失故障证据。

回归入口：`tests/test_report_integrity.py` 和两种架构的错误工单诊断保存测试。10 份已有本地报告仍可读取。

报告是静态记录，内部一致性校验不证明文件来源可信，也不会把文件重新注册成可执行的证据或授权。
